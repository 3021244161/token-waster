## 复现实验

审查时的实验脚本只监听随机的本机回环端口，每场最多 8 次调用，并设置 10 秒截止；实验输出包含实际 HTTP 峰值、许可峰值、次数、输入、输出和费用。修复后的 `node scripts/review-throughput.js` 已替换为回归断言，按场景设置最多 8 次调用与最多 4 秒截止，输出各项通过或失败。

两组改动对照只在内存中载入源文件副本，分别改变纯输入模式的输出额度和图片重复扣减，不写回生产模块。它们用于隔离原因，还不是完成适配、护栏校验和回归测试的可发布修复。

模拟器按本项目字符公式估算收到的输入，输出按请求上限回报；纯输入场景固定只回报 1。每次请求等待 80 毫秒，不模拟真实服务分词、共享速率配额、图片解析耗时或网络带宽。图片计量也使用仓库现有公式。**本地倍率不能视为真实服务的提速承诺。**

纯输入三轮输入总量分别为 3,773 / 3,799 / 3,786；对照为 10,834 / 10,889 / 10,801。当前耗时为 114 / 94 / 95 毫秒，对照为 108 / 94 / 97 毫秒，调用数均为 8。

图片场景使用 32,768 上下文、4,096 输出和 4 张 1536² 图片。每张按当前公式为 3,146，重复扣减了 12,584 的文本额度；原版与对照输出量和图片数量相同。

## 不应直接推广的尝试

另做过“将剩余总量除以空闲槽数”的单行内存试验：8 路、总目标 16,000、仅回报输出、模拟延迟等于本次输出额度除以 10 毫秒。三轮原版耗时 233 / 234 / 235 毫秒、13 次调用；对照 278 / 266 / 268 毫秒、9 次调用。

调用次数下降，但完成耗时反而增加。因此不把更换除数单独列成提速修复。应结合真实限额与延迟衡量：调用次数紧张、共享吞吐受限、单请求解码受限时，适合的粒度不同。

## 上游能力与后续方向

OpenAI Docs 说明，部分速率计算会参考声明的输出上限及输入估计，而每分钟调用数和每分钟用量是不同限制。纯输入模式声明大输出会占据并未真正使用的容量。[官方速率说明](https://developers.openai.com/api/docs/guides/rate-limits)。

Claude 官方说明，HTTP 200 后依然可能发送过载错误事件。因此负载优化依赖正确识别流内错误，不能只观察 HTTP 状态。[官方流式说明](https://platform.claude.com/docs/en/build-with-claude/streaming#error-events)。

上述缺陷修复后，再考虑在用户设定的额度和服务端批准的速率内比较输入优先、输出优先、混合三种策略；记录实际用量、耗时、费用与失败比例，用测量结果选择。任何探索调用都应计入现有次数和金额上限，保留截止与可取消等待。
