# [P1] 缺少用量回报时总量只记输出，补记输入未计入总量

状态：已闭环（2026-10-29 二次修复）。验证方式：本地模拟与当前代码路径核验。

## 本轮复核

输入记账已经补齐，但总量仍优先使用协议回退生成的非零输出小计。单次本地响应未回报用量、正文为两个字符时，最终输入为 2,048、输出为 1、总量却为 1，而分项之和为 2,049。对应代码为 src/engine.js:470–472。

这会低估总量与总量速度，并使固定总量目标持续补发。应在缺少可信总量时使用完整输入与输出之和，增加总量与分项一致性的断言；现有回归只核对输入与费用，未发现这一缺口。下文保留原始问题与修复记录。

## 位置

src/protocols/http.js:144–150；src/engine.js:419–440。行号以审查时工作区为准。

## 现象与证据

模拟服务返回简短正文但不返回用量。三次调用后，输入账本为零，费用账本为 0.000006；预算为 0.0001。按同一估算器和价格表，已发送输入约值 0.001695，账本却仍低于预算。

## 原因与影响

回退只估算输出文字，没有估算输入；结算随后释放本次全部预扣，按缺失的输入数据计算为零费用。

兼容服务省略用量时，大输入模式会严重少记用量与费用，金额限制和总量目标都可能失效。

## 复现步骤

1. 让本地模拟服务返回正常流式正文，但完全省略用量回报。
2. 设置非零输入输出单价、小额预算，以及供诊断使用的有限次数。
3. 比较已发送输入估算值与结算账本。

## 修复建议

缺少可信用量时保守结算完整输入和输出，或停止运行并标记账单不确定；不要把缺失数据当作零消耗释放预算。

## 验收标准

省略用量、仅返回部分用量和中断响应均不得静默清空已发送输入的账目。

## 修复记录

规划器新增 `estInput`；结算时若上游未回报 usage，输入按实际发送的估算记账，不再当作 0 释放预扣。

## 二次修复记录

`total` 不再无脑采用协议层给出的值：改为 `max(reported ? u.total : 0, input + output)`。
`finalizeUsage()` 在未回报用量时也不再伪造 `total`，避免它压过引擎补记的输入。
回归断言新增 `total === input + output`。
