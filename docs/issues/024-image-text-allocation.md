# [P2] 图片开销被重复扣除，使视觉模式留下大量可用上下文

状态：已处理（2026-10-30）。审查日期：2026-10-30。审查提交：cdff07e。

## 位置

src/engine.js:446–452、480–493。

## 证据

运行 `node scripts/review-throughput.js`，对比两个 `image-` 场景。

配置 Anthropic 协议、上下文 32,768、输出 4,096、填充比例 95%、4 张 1536² 图片、单次调用。按仓库公式，每张图片估算 3,146，图片合计 12,584。

当前规划先得到纯文本输入 16,088，却再次扣除图片 12,584 和固定开销 400，最终只生成约 3,104 的填充文本。应扣除的固定开销只有 400，填充目标应为 15,688。预扣账本则仍按输入 28,672 规划。

实际发出的内容由仓库字符估算器计数：原版总用量 20,300；内存对照仅移除重复扣减后为 32,498。输出均为 4,096，图片数均为 4。单次总量估算增加约 **60%**，不代表真实服务耗时不变。

## 原因与影响

上下文规划阶段已经为图片留过空间，后面的文本填充阶段又扣了一次。图片越多，文本损失越大，极端情况下填充被截成零。账本因此预扣了未实际发送的文本额度，进一步压低其他工作槽的可用预算。

## 建议

统一纯文本量、图片量和固定提示量的定义，图片只计入一次。预扣输入必须与实际构造的请求一致；修正后仍需保留上下文余量及金额限制。

## 验收

覆盖无图、混合、多图和有限金额场景；增加图片后，文本减少量应与图片占用和明确的填充策略一致，不能被扣两遍。报告中注明图片和文本用量均为估算，真实结算以服务端回报为准。

## 修复记录

固定提示、文本、图片分别规划，图片只计入一次；填充按本地估算器准确截断，再用相同口径预扣。专项模拟得到输入 28,608、输出 4,096，总量 32,704，位于 32,768 上下文以内；另验证小额预算会去掉放不下的图片。

复现脚本已改为验证修复后的回归断言；原始失败数字保留在本文作为历史证据。完整自测 46/46 通过，本轮专项 15/15 通过，均使用本地模拟服务。
