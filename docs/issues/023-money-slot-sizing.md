# [P2] 金额限制未按空闲工作槽分配，配置并发被预扣串行化

状态：已处理（2026-10-30）。审查日期：2026-10-30。审查提交：cdff07e。

## 位置

src/engine.js:411–423、465–499；src/engine.js:388–393。

## 证据

运行 `node scripts/review-throughput.js`，查看 `money-current`。

配置并发 8、仅金额限制 0.01 美元、上下文 200,000、最大输出 8,000、文本填充 5%，并保留 8 次调用和 10 秒截止。模拟器按收到的文本估算输入，并按声明额度回报输出，每次等待 80 毫秒。

初次复现：实际 HTTP 峰值并发 **1**，界面所用的许可峰值却是 **8**，2 次调用约 228 毫秒。首个请求预留约 0.0113 美元，已经占住整个 0.01 美元额度。

## 原因与影响

当前仅将剩余用量除以许可数。金额约束仍针对全部剩余金额缩放一个请求，随后再增加 15% 预扣余量。即使用量目标为无限，金额目标仍可把第一笔计划缩放到占满预算，其余工作槽等待结算。

许可统计在等待预算前就增加，不能证明实际发送并发已经打开。这个问题在小额金额目标和接近结束时尤其明显。

## 建议

金额与用量共同按实际空闲工作槽规划，计算时预先计入余量、固定提示开销和最低输出费用。配不满全部工作槽时应诚实显示实际发送数，并在结算后重新分配，保持总预扣不超出可用金额。

先处理 [027](027-minimum-request-cost.md)，避免为了提高并发而放大小额超支。

## 验收

在本地模拟器中分别观察配置并发、实际 HTTP 并发和预算占用；足够支付多个最小请求时应能打开多个工作槽。各时间点已结算加已预扣金额不得高于上限，不应仅断言许可峰值。

## 修复记录

金额按当前可用工作槽及可支付的最小请求数分配，先扣除 15% 预留余量，再缩放可变部分。实际请求通过发送前后回调配对统计，界面与报告改为显示实际发送并发。专项模拟配置 8 路时实际峰值达到 8，结算约 0.00818 美元，未超过 0.01 美元上限。

复现脚本已改为验证修复后的回归断言；原始失败数字保留在本文作为历史证据。完整自测 46/46 通过，本轮专项 15/15 通过，均使用本地模拟服务。
