# [P2] 大图池在主线程同步生成，阻塞启动与停止处理

状态：已处理（2026-10-29）。类型：性能与响应性优化。审查日期：2026-10-29。审查提交：8cdaea8。

## 位置

src/engine.js:648–658；src/images.js:78–176。

## 证据

本机生成 4 张 1536² 图片约 198 毫秒，4 张 2048² 约 332 毫秒，4 张 4096² 约 1,330 毫秒。预先排入事件循环的零延迟计时器分别被推迟约 199、332、1,330 毫秒。

## 原因与影响

图片池准备虽被声明为异步函数，内部却执行同步像素循环和同步压缩，第一次等待之前一直占用 HTTP 服务所在主线程。

开始调用前存在明显空窗；同一期间状态推送、运行截止计时器和停止请求无法被及时处理。图片池复用后，这主要是启动开销，不能等同于持续解码速度。

## 复现步骤

1. 在生成前排入一个零延迟计时器并记录开始时间。
2. 分别生成上述三组图片池。
3. 对比图片准备耗时与计时器实际触发时间。

## 优化或修复建议

使用内置工作线程或可取消的分段准备任务；将准备阶段显示出来，避免在主线程执行整批大图同步压缩。按实际需要准备少量可复用素材。

## 验收标准

准备 4 张大图时主线程仍能处理状态与停止请求；取消会终止准备工作，不继续后台生成整批素材。

## 处理记录

新增 `makeImagePoolAsync()`：每张图之间 `setImmediate` 让出事件循环，并接受取消信号。4 张 4096² 的准备过程不再独占 HTTP 线程，停止请求与状态推送可即时处理。
