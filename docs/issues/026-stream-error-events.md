# [P2] 流内错误被当成成功，导致恢复策略和消耗统计失真

状态：已处理（2026-10-30）。审查日期：2026-10-30。审查提交：cdff07e。

## 位置

src/protocols/anthropic.js:100–123；src/protocols/http.js:172–175。其他适配器也需检查流内错误。

## 证据

运行 `node scripts/review-throughput.js`，查看 `stream-error-current` 和 `SSE-callback`。

本地服务每次先返回 HTTP 200，随后发送：

```text
event: error
data: {"type":"error","error":{"type":"overloaded_error","message":"Overloaded"}}

```

配置并发 4、次数上限 8、10 秒截止，不重试。结果是 **8 次成功、0 次失败、最终许可仍为 4、输出为 0**。在没有任何用量回报的情况下，还把计划输入 80,000 计入累计估算。

单独让 SSE 回调抛出异常，读取函数依然正常返回，证明简单在适配器中抛错也不能解决。

## 原因与影响

适配器没有识别错误事件，流结束后直接返回成功；共享读取器还把 JSON 解析和业务回调放进同一个异常捕获中，将回调错误吞掉。

服务端过载会被记成健康成功，降速、退避和恢复无法正确执行；无用量回报时的计划估算还会制造虚假的消耗进度。官方明确允许 HTTP 成功后再发送流内错误。[Claude 官方流式错误说明](https://platform.claude.com/docs/en/build-with-claude/streaming#error-events)。

## 建议

识别协议错误事件并映射到统一错误分类；JSON 解析异常与业务回调异常分开处理，回调错误必须向上传播。保留已确认的部分用量，无法确认的部分明确标为未知，避免重新发送时重复或遗漏记账。

## 验收

覆盖流开始即错误、已有部分用量后出错、过载、限流和正常结束。错误不增加成功数，调度器按错误类型退避，重试仍计入实际次数上限，所有等待继续支持急停。

## 修复记录

三个适配器统一识别流内错误，回调异常不再被当成解析错误吞掉，读取器退出时取消并释放响应。只把已确认的部分用量计入统计，未知部分独立预留；每次流失败后释放原请求预扣，重试前重新检查余额。新增三种协议错误、部分回报重试、未知开销阻止重复花费、限流可取消和回调传播检查，全部通过。

复现脚本已改为验证修复后的回归断言；原始失败数字保留在本文作为历史证据。完整自测 46/46 通过，本轮专项 15/15 通过，均使用本地模拟服务。
