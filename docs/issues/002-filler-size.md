# [P1] 填充缓存的最小分档导致小额度请求严重超额

状态：已修复（2026-10-29）。验证方式：本地模拟与当前代码路径核验。审查日期：2026-10-29。

## 位置

src/engine.js:626–637；src/prompts.js 的 buildPayload。行号以审查时工作区为准。

## 现象与证据

单工作线程，总量目标为 1,000，上下文为 200,000，最大输出为 8,000，填充率为 20%。模拟服务按项目自身估算器统计收到的文本，单次输入约为 24,900，最终回报总量约为 24,943。随机文本会使具体数字略有变化。

## 原因与影响

规划器按缩小后的目标量预扣，但填充缓存至少生成一个 25,000 的分档。组装正文时直接采用整份缓存文本，没有裁剪到规划大小。

真实正文远大于预扣值，破坏总量目标、费用限制和上下文限制；这不是最后一次调用的轻微估算误差。

## 复现步骤

1. 让本地模拟服务使用项目估算器计算收到的全部文本，并回报这一用量。
2. 采用上述参数并限制最多一次调用。
3. 比较目标 1,000、预扣值与实际收到的正文估算量。

## 修复建议

缓存文本在使用时必须按本次规划裁剪；发送前根据最终正文重新核对预扣，并包含随机前缀与固定指令的开销。

## 验收标准

覆盖小于一个分档、恰好一个分档和接近上下文上限的情况；最终正文的估算量须与规划一致，不能因缓存分档而膨胀。

## 修复记录

`#fillerFor()` 在返回前按本次规划 token 数裁剪缓存文本，不再整份下发；分档改为向上取整以便复用。验证：目标 20k、单请求，输入均值回落到 20k 以内。
